iGARO MVP Technical White Paper v1.0

 ​Nov 21, 2026 · ​@INNOSOM
iGARO is a multi-tenant SaaS platform that lets institutions issue, manage, suspend,
revoke and publicly verify digital credentials. Every credential is cryptographically signed
by the institution that issued it, so anyone can confirm it is authentic and still valid in
seconds by scanning a QR code.
This version replaces the v0 paper. The MVP has no blockchain layer: trust comes from
institution digital signatures, published public keys and a tamper-evident audit log. The
design keeps a clean slot for blockchain anchoring, which is planned as the first Phase 1
feature.

1. Problem and solution

Physical ID cards and PDF certificates are easy to copy, edit or fake, and checking one
usually means contacting the institution that issued it.
For verifiers (employers, universities, hospitals, security officers), the question is: "Was
this really issued by this institution, and is it still valid?" Today there is rarely a fast, reliable
way to answer it.
For institutions, there is no single system to issue credentials, manage holders, revoke or
suspend credentials, keep a history, and offer a trusted public check.
iGARO's answer is a managed credential lifecycle: create, issue, deliver, present, verify,
then suspend, reinstate, revoke or reissue as needed. Each credential is signed with the
institution's own key and carries a QR code. Scanning it opens iGARO's public verification
page, which shows whether the credential is authentic, unaltered and currently valid.
The product is a credential management and verification platform, not "a blockchain
database for ID cards". The institution uses iGARO, the holder uses the digital credential,
and the verifier uses the verification page.

2. Actors and credential lifecycle

iGARO has three actors. The institution (for example East Africa University) issues
credentials through its dashboard. The credential holder (for example Ahmed Hassan)
receives the credential and presents it. The verifier (an employer, university, hospital or
security officer) scans the QR code to check it.

Suspension is for temporary situations, such as a student on leave, and can be undone.
Revocation is for fraud or a rescinded degree, and is final, so a verifier can always trust a

never deleted; they stay in the system for the audit trail.

3. MVP scope

The MVP proves one thing: an institution can issue a signed digital credential, and
anyone can verify it, and see it suspended or revoked, by scanning a QR code.

It targets one vertical first: education (universities, colleges, training centres), where
fake certificates are the clearest fraud problem. It ships two templates, a Student/Staff ID
card and a Certificate. Credential types are configuration, so hospitals and companies
later need setup, not new code.

4. Trust model without blockchain

A verifier needs four answers: does the credential exist, did this institution issue it, has it
been altered, and is it still valid. The MVP answers all four with standard cryptography and

Key protection. Each institution's private key is encrypted with AES-256-GCM under a
master key held outside the database (a cloud key-management service in production). It
is never stored or logged in plaintext. Keys carry an ID so they can be rotated; old keys
stay published as retired so older credentials still verify. A leaked key is marked
compromised, which makes every credential it signed fail verification.

Known limits until Phase 1. Signatures prove authenticity independently of iGARO, but
revocation status still depends on trusting iGARO's servers, and outside timestamps
cover the audit log once a day rather than each credential. Phase 1 closes both by
anchoring credential hashes and status on a public blockchain.

5. System architecture

The MVP is a conventional web platform: one web app, one API, one PostgreSQL database
and one background worker. Blockchain sits outside it as a future add-on.

MVP system architecture

The API is the only component that signs credentials. It unlocks an institution's private
key with the master key only at the moment of signing. The worker handles slow tasks
(emails, card rendering, CSV imports) through a job queue stored in PostgreSQL, so no
extra queue server is needed. In Phase 1 the same worker gains an anchoring job that
writes credential hashes and status to the blockchain.

6. Credential data, hashing and signing

Every credential stores one canonical payload: the exact data that is hashed and signed.
Status, tokens and branding are kept outside it, so they can change without breaking the
signature.

  1. Canonicalize the payload with RFC 8785 (JSON Canonicalization Scheme), so the
     same data always produces the same bytes.

  2. Hash it: dataHash = SHA-256(canonical payload) .
  3. Sign it: signature = Ed25519(institution key, "igaro.credential.sig.v1:" +

     dataHash) . The prefix stops the signature being reused in another context.
  4. Store the payload, dataHash , signature and key ID with the credential.

Three details matter:

     Salt. A random 256-bit salt stops anyone guessing the hash from a name and an ID
     number. Deleting the salt later makes the hash permanently unlinkable to the person,
     which supports data-deletion requests.
     Photo hash. The SHA-256 of the photo is signed, so swapping the photo is detected.
     No in-place edits. Signed data never changes. A correction is a reissue: a new
     credential is created and the old one becomes SUPERSEDED, pointing to the new one.

The canonicalize, hash and sign code lives in one shared package, used by issuance,
verification and the open-source verifier, and is covered by golden tests. Changing its
output requires a new schemaVersion .

7. Issuing a credential

Issuance completes in under a second, with no waiting on any external network.
What the institution admin does

  1. Log in and open the dashboard.
  2. Create or select the credential holder, and upload their photo.
  3. Choose the credential type (ID card or certificate) and fill in its fields.

                                                                                  Page 6 of 15
iGARO MVP Technical White Paper v1.0

  4. Click Issue. For many holders, upload a CSV file and a ZIP of photos instead, check the
     preview, then issue the batch.

What the system does, in one database transaction
  1. Validate the fields against the credential type's attribute list.
  2. Generate the internal ID, the printed credential number, a 128-bit verification token
     and a separate holder token.
  3. Build the canonical payload with a fresh salt and the photo hash.
  4. Hash and sign it with the institution's active key.
  5. Save the credential as ACTIVE, and write a lifecycle event and an audit-log entry
     (audit entries are written one at a time per institution, using a database lock, so the
     chain never forks).

After the transaction (background jobs)
  1. Render the branded card as PNG and PDF, with the QR code.
  2. Email the holder a private link to view and download the card and the signed
     credential file.
  3. (Phase 1) Anchor the credential hash on the blockchain.

8. Public verification

The verification page is the most important screen in the MVP: it is what a verifier sees in
the first seconds after scanning.
QR code. The QR contains only a URL with a random 128-bit token, for example
 https://verify.igaro.app/v/Xq3... , and never the credential data. The printed
credential number is for people to read and is never used for lookups, so URLs cannot be
guessed or enumerated. The card also says "Verify only at verify.igaro.app" to guard
against fake QR codes.
Checks, in order

  1. Exists? Look up the token. Missing, or still a draft → NOT FOUND.
  2. Unaltered and authentic? Recompute the hash from the stored payload and check

     the institution's signature. Mismatch → VERIFICATION FAILED, and the operations
     team is alerted.
  3. Key still trusted? The signing key is marked compromised → VERIFICATION FAILED.
  4. Status? REVOKED, SUSPENDED or SUPERSEDED → shown as such, with a link to the
     replacement for SUPERSEDED.
  5. Expired? The signed expiry date has passed → EXPIRED.

                                                                                                                                                                                                                                            Page 7 of 15
iGARO MVP Technical White Paper v1.0

  6. Institution in good standing? Institution suspended on iGARO → VALID, with a
     warning.

  7. Otherwise → VERIFIED.

Integrity is checked before status, so a tampered record can never appear as a clean
"revoked" result. Every check is logged with a hashed IP address.

Each institution chooses which fields the page shows. Name and status always appear;
photo, ID number and attributes are optional. The page also offers the signed credential
file for download and links to the institution's public keys, so the signature can be
checked independently. A Blockchain proof line is already part of the page design and
will read "Not anchored" until Phase 1.

9. Multi-tenancy, roles and security

Tenant isolation. Institution A must never see Institution B's data. Every tenant table
carries institution_id , and isolation is enforced in two independent layers:

  1. The data-access layer takes the institution from the logged-in session, never from the
     request.

  2. PostgreSQL Row-Level Security blocks any query that reaches another tenant's rows,
     even if the application has a bug.

     Passwords hashed with Argon2id; login rate limiting; sessions in httpOnly, Secure

     change out of REVOKED.
     No private key, salt or token ever written to logs.

A one-page threat model covers forged cards, insiders editing the database, a
compromised server, URL enumeration, phishing QR codes, stolen admin accounts and
stolen keys, and records which threats wait for Phase 1.

Data protection. The public page shows holder names and, optionally, photos. Before a
pilot, each institution collects holder consent and signs a data-processing agreement
with iGARO. Under laws such as Kenya's Data Protection Act 2019, the institution is the
data controller and iGARO the data processor.

13. Delivery plan

About 5 weeks for 2 experienced developers (about 8 weeks for one), about 2 weeks
less than a build with blockchain, and without its riskiest parts (smart contract, wallets,
gas fees, network outages).

  1. Week 1, foundations: repository, automated checks, Docker Compose, database
     schema with Row-Level Security, login and invites, threat model, decision records.

  2. Week 2, institutions and holders: institutions, branding, signing keys, holders, photo
     storage, credential types.

  3. Week 3, the trust core: canonicalize, hash and sign with golden tests; issuance;
     lifecycle; event log; hash-chained audit log with a signed daily head hash.

  4. Week 4, verification: public verification page, proof panel, public keys, signed
     credential download, open-source verifier, rate limiting.

  5. Week 5, delivery and polish: card rendering (HTML card first, then PNG and PDF
     through headless Chrome, with QR), holder email and link, CSV bulk import,
     dashboard figures, hardening, staging deployment, demo script.

Each module has written acceptance criteria ("given …, when …, then …"), and the full
demo runs as an automated test so it never breaks before a meeting.
