# W3 acceptance: trust core, issuance, lifecycle, audit
- Given golden test vectors, when canonicalize/hash/sign run, then outputs are byte-identical to the committed fixtures.
- Given a valid issue request, when POST /credentials, then in one transaction an ACTIVE credential with unique number, 128-bit token, separate holder token, salt, dataHash, signature, kid, an ISSUED event and an audit entry exist; response under 1 second.
- Given a failure after signing, when the transaction rolls back, then no credential, event or audit entry remains.
- Given ACTIVE, when suspended with reason then reinstated, then status goes SUSPENDED then ACTIVE and both events and audit entries exist; without a reason, 422.
- Given ACTIVE, when revoked, then REVOKED; when reinstate is attempted, then 409; when status is updated directly in SQL, then the trigger refuses it.
- Given ACTIVE, when reissued, then old is SUPERSEDED with superseded_by and the new is ACTIVE.
- Given concurrent issuances, then audit chain has no forks and verify-chain passes.
- Given an audit entry edited and all later hashes recomputed, when verify-chain runs, then mismatch with the signed daily head is reported.
- Given the daily job, then a signed head hash and OpenTimestamps proof are stored per institution.
- Given logs, then no private key, salt or token appears.
