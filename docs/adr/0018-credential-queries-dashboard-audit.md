# ADR 0018: Credential list/get, dashboard stats, audit logs, verify-chain (T-027)

Status: accepted. Every choice below is the recommended option, taken under the owner's standing permission.

## Decisions
1. **Tenancy.** `apps/api/src/credential-queries.ts`; the institution comes from the session only, every query runs in `Db.withTenant` and filters on `app_institution_id()`. Another tenant's, unknown and malformed ids are the same 404 body. Institution Admin only; responses are `Cache-Control: no-store`.
2. **No secrets.** Responses never contain the verification token, the holder token or its hash, the salt, or photo/storage keys. The signed `payload` is therefore not returned whole (it holds the salt). The detail returns `attributes`, `dataHash`, `signature`, `issuerKeyId`, `anchorStatus` and the holder/type summary. The verification token is obtained by the card/verify flows, not by this API (docs/api.md issuance row). The detail's `events` carry only the stored event payload (from/to, dataHash, kid, supersededBy, reissuedFrom).
3. **Computed status.** `status` in list, detail and stats is `EXPIRED` when the stored status is `ACTIVE` and `expires_at <= now()` (invariant 7: SUSPENDED/REVOKED/SUPERSEDED win over EXPIRED). The detail also returns `storedStatus`. The filter `status=EXPIRED` matches the computed value and `status=ACTIVE` excludes expired credentials, using the same SQL expression as the stats, so list filter and dashboard counts always agree. No stored status is changed by reading.
4. **Search `q`.** Case-insensitive substring (ILIKE) over `credential_number` and the holder's `full_name`; trimmed, NFC, max 100 characters, control/format characters rejected (400 `INVALID_SEARCH`); `%`, `_` and `\` are literal. An empty/blank `q` means no filter. `type` is the type code (`^[A-Z][A-Z0-9_]{1,39}$`, else 400 `INVALID_TYPE`); an unknown code returns an empty list. Filters combine with AND. Unknown query parameters are 400 `UNKNOWN_PROPERTY`.
5. **Pagination.** Keyset, as docs/api.md prescribes (`?cursor=&limit=`), returning `{items, nextCursor}` (`nextCursor` null on the last page). `limit` is 1-200 (default 50); anything else is 400 `INVALID_LIMIT` rather than silently clamped. Credentials sort `created_at DESC, id DESC`; the cursor is an opaque base64url of the microsecond-precision `created_at` plus id (so no ties are lost) and is strictly validated (400 `INVALID_CURSOR`). Audit logs sort `seq DESC` and the cursor encodes the last `seq`. No `total` count is returned (a count over a growing table on every page is avoided); stats give totals. This differs from `/holders`, which predates the contract's cursor convention and uses offset.
6. **Dashboard stats.** `{total, byStatus}` with every status key present (zero when empty), including computed `EXPIRED`.
7. **Audit log list.** Own chain only (`entryHash`, `prevHash`, `seq`, action, target, metadata, actor, time). The hashed IP is not returned. Metadata was already screened for secret-looking keys at write time (ADR 0015).
8. **verify-chain.** Recomputes the full chain with `verifyAuditChain` (core `verifyChain`). It then compares with `audit_head_hashes` rows (written by the T-028 worker job): each signed `head_hash` must still be an `entry_hash` in the chain, which catches a chain that was rewritten and re-hashed after the head was signed. Response: `{valid, entries, head | {brokenAtSeq, reason}, headsRecorded, signedHeads:{checked, matched, mismatchedDays[]}}`. `headsRecorded` is true only when at least one head exists and all match; with no rows the endpoint reports chain validity and `headsRecorded:false`. `valid` is false on a broken chain or any mismatched head. This endpoint does not verify the head signatures or OpenTimestamps proofs (signer key policy and proof upgrade belong to T-028/T-029); it only proves chain consistency against the recorded heads. The whole chain is read per call, which is acceptable for the MVP volume; a checkpoint from the latest verified head is a later optimisation.
