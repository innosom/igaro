# ADR 0016: Single credential issuance (T-025)

Status: accepted. Every choice below is the recommended option, taken under the owner's standing permission.

## Decisions
1. **One code path.** `issueInTransaction(client, ctx, input)` in `apps/api/src/credentials.ts` does everything inside the caller's `Db.withTenant` transaction: institution status, holder and type (`FOR SHARE`), attribute validation, ACTIVE key (`FOR SHARE`, so a rotation waits), credential number, payload, hash and sign, credential row, `ISSUED` event, audit entry. `POST /credentials` and the later internal batch path (T-043/T-044) both call it. The institution comes from the session object; the body may not carry it (unknown properties are 400).
2. **Request body** is `{holderId, credentialTypeCode, attributes, expiresAt?}` (docs/api.md). Unknown holder or type code, a foreign tenant's, or a malformed holder id are all 404.
3. **Holder photo is required.** `igaro.credential.v1` requires `holder.photoSha256` (64 hex), so a holder without a photo gets 409 `HOLDER_PHOTO_REQUIRED`. Certificates need a photo too in the MVP; a nullable photo hash would need a new `schemaVersion`.
4. **Photo blocker (T-018 review M1) closed by keeping objects, not refusing.** Photo keys are now content-addressed (`.../photo/<sha256>.<ext>`). Replacing a photo no longer deletes the previous object when any credential of the holder has its hash in `payload.holder.photoSha256` (or when the new object is the same key). Verify and card can therefore find the committed photo by hash and must only show a photo whose SHA-256 equals the payload's. Refusing replacement with 409 was rejected: after issuance the holder could never get a new photo, even for a reissue. Unsigned photos are still cleaned up. A failed DB update after the upload no longer deletes the new object (it may be the one already in use). The JPEG allow-list (L1) was done in ADR 0010.
5. **Credential number** is `YYYY-NNNNNN`: the issuing year and a per-institution running number (max existing suffix + 1, six digits minimum). It is computed under a per-institution transaction advisory lock (`igaro.credno:<institution>`), taken before the audit lock, so parallel issuances never duplicate; the unique `(institution_id, credential_number)` index is the backstop. A rolled-back issuance consumes no number. No migration or counter table. Human-readable only, never used for lookup.
6. **Tokens.** Verification token and holder token are 16 random bytes each, base64url (22 chars, 128 bits). The verification token is stored in clear (QR/card). The holder token is stored as SHA-256 hex only (ADR 0002) and its plaintext is returned once, in the 201 response, so T-040 can hand it to the delivery job. Neither goes into the event payload, audit metadata or logs.
7. **Attributes.** Validated against the type's stored schema, re-validated with `parseAttributes` (T-019 L2; an invalid stored schema is 409 `TYPE_SCHEMA_INVALID`) and read with `Object.hasOwn` (L4). Unknown keys 400; required missing 400; optional absent are omitted from the payload. All values become strings: text is NFC-normalised, trimmed, 1-500 chars with control, bidi/format characters and lone surrogates refused (ADR 0013 follow-up); dates are real `YYYY-MM-DD`; numbers are finite, at most 15 integer and 10 fractional digits, written in plain decimal. Holder `fullName` and `externalId` are NFC-normalised in the payload.
8. **Expiry.** `expiresAt` omitted uses the type's `validity_days` from now (none if null); `null` means no expiry; a value must be strict `YYYY-MM-DDTHH:MM:SSZ` and later than the issue time. `issuedAt` is the server time truncated to seconds, identical in the payload and the row.
9. **Signing.** The private key is unwrapped only inside the signing step with the master key and kid binding, signed with core's `signCredential`, then checked with `verifyDataHashSignature` against the stored public key (a mismatched key row fails closed). Any failure is 500 `SIGNING_FAILED` with a fixed message; no master key is 503 `KEY_CUSTODY_UNAVAILABLE`; no ACTIVE key (none, or only RETIRED/COMPROMISED) is 409 `NO_ACTIVE_KEY`.
10. **Suspended institution cannot issue** (409 `INSTITUTION_SUSPENDED`); the white paper only defines the verification warning, and issuing new credentials while suspended is the safer reading.
11. **Event and audit.** `credential_events` gets an `ISSUED` row (payload: number, dataHash, kid) with `anchor_status` left `NOT_ANCHORED` on the credential. Audit action `credential.issued`, target the credential id, metadata `{credentialNumber, credentialType, holderId, kid, dataHash}` plus the hashed IP. Metadata key names avoid the deny-list (ADR 0015).
12. **Not in this task.** Enqueueing the card render and email jobs after commit is T-040; the 201 response contains what those jobs need. List/get is T-027.

## Follow-ups
- T-040 must enqueue jobs only after commit and pass the holder token only through the job, clearing it once sent.
- T-043/T-044 batch path must call `issueInTransaction` (one transaction per row) behind service authentication.
- Verify (T-032) and card (T-039) must resolve the photo by `holder.photoSha256`, not by the holder's current `photo_key`.
- The response carries `payload`, `dataHash` and `signature`; do not log response bodies.
