# ADR 0019: Daily audit head hash, signing and OpenTimestamps (T-028)

Status: accepted. Every choice below is the recommended option, taken under the owner's standing permission.

## Decisions
1. **Job.** `audit.dailyHead` (`apps/worker/src/audit-head.ts`) is a pg-boss scheduled queue (default `10 0 * * *` UTC, `AUDIT_HEAD_CRON`), retried with exponential backoff (6 tries). One run handles every chain: each institution plus the NULL platform chain. Each chain runs in its own transaction with RLS settings (`app.institution_id`; platform scope only to list institutions and to write the NULL chain). A failure on one chain does not stop the others; the run then fails so pg-boss retries, and finished chains are skipped. The job is idempotent: one head per (chain, UTC day) via `audit_head_hashes_chain_day_uniq` and `ON CONFLICT DO NOTHING`; a manual `boss.send('audit.dailyHead')` is safe.
2. **Signer: the platform head key, not institution keys (deviation from the task text, deliberate).** The task asked for the institution's active key. The worker rules (v1.0 section 5, worker charter) say the worker never holds or unwraps institution signing keys, and `institution_keys` stays unreadable to `igaro_worker`. Heads are therefore signed by one **platform** Ed25519 key: an `igaro.key.v1` envelope under the separate secret `AUDIT_HEAD_WRAP_KEY` (see decision 9; `AUDIT_HEAD_SIGNING_KEY`, bound to `AUDIT_HEAD_KEY_ID` as AAD), unwrapped once per run and dropped. Side benefit: an institution admin, or a compromised institution key, cannot forge a head for its own chain, and the platform chain gets a signature too. The public key is configured on the API (`AUDIT_HEAD_PUBLIC_KEYS=kid:key,...`); rotation keeps old kids. If the owner prefers institution-key signing, the API must do it (it is the only component that signs); say so and it becomes a follow-up task.
3. **Signed message (domain separated).** `"igaro.audit.head.sig.v1:" + (institutionId | "platform") + ":" + day + ":" + headHash` (`auditHeadMessage`, `signAuditHead`, `verifyAuditHeadSignature` in `packages/core/src/audit-chain.ts`, golden-tested). It differs from `igaro.credential.sig.v1:` so a credential signature never verifies as a head, and the chain id and day are bound so a head cannot be replayed elsewhere.
4. **Proof storage: a separate append-only table (option chosen).** `audit_head_hashes` refuses UPDATE, so `ots_proof` there is left unused (NULL). New table `audit_head_timestamps(head_id, institution_id, state PENDING|COMPLETE, ots_proof)`, unique per (head, state), no UPDATE/DELETE/TRUNCATE (trigger and grants), RLS select for the tenant/platform, a trigger forcing the row's institution to equal its head's. Flow: submit, insert PENDING; on later runs upgrade, insert COMPLETE. The PENDING receipt is never rewritten. Considered and rejected: a second head row per day (breaks the one-head-per-day rule and the T-027 matching) and relaxing the append-only trigger for `ots_proof` (weakens the audit guarantee).
5. **Timestamper interface.** `Timestamper { enabled, submit(digest), upgrade(proof) }` in `ots.ts`. `NoopTimestamper` (default outside production; tests) stores nothing; `CalendarTimestamper` talks to calendar HTTP servers through an injectable `fetch` (`OTS_CALENDAR_URLS`; unset means the public alice/bob/finney calendars in production only, `disabled` turns it off). The digest stamped is `SHA-256(auditHeadMessage)`; only that 32-byte digest leaves the host. The stored value is a standard `.ots` file (magic, version 1, SHA-256, digest, tree) readable by the reference client. Submit tries calendars in order and keeps the first valid receipt (single chain). Upgrade fetches `GET {calendar}/timestamp/{commitment}`, accepts it only if it carries a Bitcoin attestation, and splices it over the pending attestation. Limits: forked multi-calendar proofs are not upgraded by this client, the pending URI must equal a configured calendar (SSRF guard), redirects are refused, responses are capped at 256 KB with a 10 s timeout. Failed submits or upgrades do not fail the head: the head stays without a proof row and the next run retries (the run is still reported as failed so it backs off).
6. **Worker-only writes (T-027 follow-up).** Migration `20261126000000_audit_head_timestamps`: creates NOLOGIN role `igaro_worker` (grant LOGIN out of band, like `igaro_app`; point `WORKER_DATABASE_URL` at it), revokes INSERT on `audit_head_hashes` from `igaro_app`, replaces the insert policy with one `TO igaro_worker` (own chain via `app.institution_id`, NULL chain only in platform scope). `igaro_worker` grants: SELECT on `institutions`, `audit_logs`; SELECT+INSERT on the two head tables; nothing else (no keys, sessions, users, credentials). The API role keeps SELECT. The harness gained `asWorker` and `audit_head_timestamps` in `TENANT_TABLES`.
7. **verify-chain checks signatures (T-027 follow-up).** `signedHeads` now also reports `signaturesVerified`, `signatureInvalidDays` (wrong signature for a configured kid: `valid:false`) and `signatureUnverifiedDays` (kid with no configured public key: reported, not treated as tampering, so deployments without `AUDIT_HEAD_PUBLIC_KEYS` still work). OTS status is not exposed by the API yet.
8. **Logging.** Only ids, counts, SQLSTATE and our own OtsError text are logged (driver messages can echo row values). No key, envelope, signature or token is logged.
9. **Security review hardening (recommended option taken under the owner's standing permission).**
   - **H1 separate wrap key.** The head key envelope is wrapped under `AUDIT_HEAD_WRAP_KEY` (same format as `MASTER_KEY`: base64, 32 bytes), never `MASTER_KEY`. The worker does not read `MASTER_KEY` at all, so a worker compromise cannot unwrap institution keys, and the master key never reaches the worker host. `WorkerConfig.auditHead` carries `wrapKey`, not a master key.
   - **M1.** When `AUDIT_HEAD_PUBLIC_KEYS` is configured, verify-chain treats a head with an unknown `signer_kid` as a failure (`valid:false`, `headsRecorded:false`); only deployments with no keys configured keep reporting it as unverified. The API refuses to start in production without `AUDIT_HEAD_PUBLIC_KEYS`.
   - **M2.** In production the head job needs `WORKER_DATABASE_URL` (the `igaro_worker` login); config fails otherwise. At startup the worker runs `has_table_privilege(current_user, 'audit_head_hashes', 'INSERT')` and refuses to start the job if false.
   - **M3.** The OTS parser caps `varbytes` operands and every intermediate message at 4096 bytes (hexlify doubling and appends cannot grow memory).
   - **L1.** Calendar URLs must be https when `NODE_ENV=production`. **L2.** Calendar responses are streamed and abandoned at the 256 KB cap. **L3.** `MASTER_KEY` removed from worker config and env.

## Follow-ups
- Platform: create the `igaro_worker` login and point `WORKER_DATABASE_URL` at it; this also unblocks the T-011 pg-boss schema follow-up. Provision `AUDIT_HEAD_SIGNING_KEY` and `AUDIT_HEAD_WRAP_KEY` (production start fails without them) and publish its public key to the API.
- Expose proof status and the `.ots` download (platform/admin endpoint) and run `ots verify` in a QA test (T-029). Verify-CLI could check head signatures offline (T-034).
- Platform chain heads are signed but have no API endpoint yet.
- A head is taken at the run time (00:10 UTC) for that UTC day; entries after it are covered by the next day's head. Multi-calendar (forked) proofs and RIPEMD-160 paths are untested against live calendars (no network in tests).
- verify-chain head position check (head must not precede the last signed head's seq) remains open.
