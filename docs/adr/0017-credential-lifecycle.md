# ADR 0017: Credential lifecycle endpoints (T-026)

Status: accepted. Every choice below is the recommended option, taken under the owner's standing permission.

## Decisions
1. **Code path.** `apps/api/src/credential-lifecycle.ts`. Each action runs in one `Db.withTenant` transaction: lock the credential row (`FOR UPDATE`, tenant filtered, so concurrent actions serialise), ask `@igaro/core` `planTransition` whether it is allowed, insert the `credential_events` row, then update `credentials.status`, then append the audit entry. The DB triggers (event in the same txid, one status change per credential per transaction, REVOKED immutable) remain the backstop.
2. **Errors.** Missing, blank, non-text, over 500 characters, or control/bidi-containing reason on suspend, revoke and reissue is 400 `REASON_REQUIRED` / `INVALID_REASON` (checked before the lookup, so it reveals nothing). Unknown, malformed or other-tenant id is 404. A transition core refuses is 409 `INVALID_TRANSITION`. Unknown body properties are 400.
3. **Reason storage.** The reason goes into the audit entry metadata (`reason`), not into `credential_events.payload` (that outbox is later anchored; free text does not belong in it). The event payload only has `{from, to}` and, for reissue, `supersededBy`.
4. **Reinstate** accepts an optional `reason` (stored in the audit entry if given). Suspend and revoke on a SUSPENDED credential stay 409: core allows REVOKE from ACTIVE only (ADR 0014 M4 is still an owner question; nothing was changed here).
5. **Reissue** reuses `issueInTransaction` (ADR 0016), so the new credential gets fresh id, number, tokens, salt, current holder name and photo hash, and the ACTIVE key. Body `{reason, attributes?, expiresAt?}`; `reason` is required (api.md already listed it; core does not require one for REISSUE, the API does, because it is the audit trail for a correction). Omitted `attributes` and `expiresAt` are inherited from the old signed payload, so a name or photo correction is a one-call reissue. The new credential must pass the type's current schema (400 otherwise, whole transaction rolls back).
6. **Order inside the transaction:** issue the new credential, insert `REISSUED` on the old one, set the old to SUPERSEDED with `superseded_by`, audit `credential.reissued` on the old (metadata: new id and number, reason, previous status). Only an ACTIVE credential can be superseded; SUSPENDED or SUPERSEDED is 409.
7. **Reissue after a mistaken revocation.** The DB forbids any change to a REVOKED row, and core has no REVOKED to SUPERSEDED move, so the old credential stays REVOKED with no `superseded_by`. The link lives on the new credential's `ISSUED` event payload (`reissuedFrom`) and the audit entries (`credential.issued` has `reissuedFrom`, `credential.reissued` targets the old id). A revoked credential can be reissued once (409 `ALREADY_REISSUED`, found through the `reissuedFrom` events). Verification (T-032) for a REVOKED credential therefore cannot show `supersededBy`; if the product wants that, a later migration would add a nullable `replaced_by` on credentials that is exempt from the REVOKED freeze. Left open.
8. **Response.** suspend/reinstate/revoke: 200 `{id, credentialNumber, status, previousStatus}`. Reissue: 201 `{credential, previous}` where `credential` has the POST /credentials shape (including the one-time `holderToken`) and `previous` is `{id, credentialNumber, status, supersededBy}`.
9. **Suspended institution** may still suspend, reinstate and revoke (safety actions); reissue issues a new credential and so is 409 `INSTITUTION_SUSPENDED` (ADR 0016 item 10).
10. **Key compromise re-auth (ADR 0012 M3)** is not relevant: these routes never touch key custody beyond the existing signing step, so no password re-entry is added. Authorisation is Institution Admin plus the normal CSRF check.
11. **Logging.** Only ids and the event name are logged; never the reason, tokens, salt, payload or signature.
